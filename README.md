# Rectus femoris sEMG classification

This initial code upload contains implementations of six experiments for classifying early and late exercise stages from rectus femoris surface EMG: a majority-class baseline, logistic regression on RMS and MDF, logistic regression with feature selection, a linear SVM, an RBF SVM, and a fixed 1D waveform CNN. It includes preprocessing, feature extraction, subject-wise evaluation, and scripts for generating result tables and figures.

The labels are proxies for fatigue. Class **0** represents the first third of a reviewed active interval, and class **1** represents its last third, measured in elapsed time. The middle third and windows crossing a third boundary are discarded. These labels do not constitute independently measured physiological fatigue.


## Requirements and installation

Use **Python 3.13**. Run all commands from the repository root after downloading or cloning the repository.

```sh
python -m venv .venv
```

Activate the environment in Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Or on Linux/macOS:

```sh
source .venv/bin/activate
```

Install the scientific dependencies and, if using the CNN, PyTorch:

```sh
python -m pip install -r requirements.txt
python -m pip install -r modelling/requirements_cnn.txt
```

The numerical libraries and PyTorch are pinned to the versions used in the original experiment. The CNN uses CUDA when available and otherwise runs on CPU. The nested RBF search can take considerably longer than the other feature models. Each training run records library versions, device, seeds, input hashes, and execution time; results can vary across hardware and library versions.

Every experiment can run from the command line. To use the notebooks instead, install and launch JupyterLab:

```sh
python -m pip install jupyterlab ipykernel
python -m jupyter lab
```

Select the virtual environment's Python kernel and restart it after changing packages.

## Dataset and experiment annotations

The course dataset and original review files are distributed separately through the authorized course channel. They are required inputs for reproducing the original experiment and are not included in the public repository.

### Configure the recordings

Copy `config.local.example.json` to `config.local.json` and set `raw_data_dir` to the directory containing the original participant folders:

```json
{
  "raw_data_dir": "C:/private/EMG - RAW data"
}
```

Alternatively, set the `EMG_RAW_DATA_DIR` environment variable, which takes precedence over the configuration file. Relative paths are resolved from the repository root.

Preserve the original directory structure and filenames:

```text
EMG - RAW data/
  <participant folder>/
    <original filename containing _dr_ or _iz_>.csv
```

Each CSV must contain `Relative_Time_s`, `Voltage_mV`, and `ADC_Value`. Filename tokens `dr` and `iz` identify the right and left legs. Set tokens are preserved as recording metadata; they do not identify individual repetitions. The loader expects the actual course CSV format.

### Use the original reviews

Place the original review assets at these paths **before registering the recordings or initializing preprocessing**:

| File | Purpose |
| --- | --- |
| `audit/private/subject_key.json` | Preserves the original participant-to-ID mapping. |
| `processing/annotations.json` | Contains reviewed active intervals, set exclusions, and artifact spans, with source checksums. |
| `processing/review_data/review_history.jsonl` | Preserves the review history for provenance. |

The recording registry and browser caches are regenerated by the commands below. Initialization preserves existing annotations, so no new manual review is needed when using the original files.

The original experiment contains **15 participants, 140 source recordings, 139 reviewed recordings, and one excluded recording**. Preprocessing and labelling retain **9,215 windows: 4,673 early and 4,542 late**. These counts provide a useful consistency check, although counts alone do not establish identical inputs.

### If only raw recordings are available

Raw CSVs do not encode the manual boundary and artifact decisions. Without the original reviews, register the recordings, initialize proposals, and start the review interface:

```sh
python audit/audit_data.py
python processing/pipeline.py init
python processing/review_boundaries.py
```

Open <http://127.0.0.1:8765/>. For every recording, inspect the waveform, set the start and end of sustained exercise activity, enter a reviewer ID, select **Reviewed active interval**, and save. Record artifact intervals and whole-set exclusions with signal-quality reasons. The initial RMS-based proposals remain pending until reviewed. Resolve all pending recordings, then stop the server with Ctrl+C.

Review decisions must be independent of classifier performance. A new review reproduces the analysis procedure but can produce different windows and scores from the original experiment. Use the original annotations when comparing against the reported numerical results.

## Preprocessing and model inputs

With the original recordings configured and the review files in place, run:

```sh
python audit/audit_data.py
python processing/pipeline.py init
python processing/pipeline.py run
python -m modelling.prepare_data
python -m modelling.export_cnn_signals
```

If you completed a new review using the preceding instructions, start with `python processing/pipeline.py run`.

The processing chain uses timestamp-aware segmentation, a fourth-order Butterworth bandpass design at **20–450 Hz** with forward/backward SOS filtering, **500 ms windows with a 250 ms hop**. No notch filter or MVC normalization is applied; an independent MVC reference is unavailable. The filtering is offline and noncausal.

Windows are ineligible when they violate timing or segment-edge rules, contain nonfinite values, overlap an ADC flatline lasting at least 20 ms, or overlap a reviewed artifact interval. Whole-set exclusions follow the saved annotations. Parameters are stored in `processing/config.json`.

The shared implementation in `feature_explorer/explore_features.py` computes 36 candidate descriptors. Processing exports their definitions and units in `feature_dictionary.csv`, together with window features, QC logs, provenance, and feature trajectories. The model-data exporter assigns the temporal labels and retains only complete eligible windows within reviewed early or late thirds.

The CNN exporter reconstructs the corresponding **500-sample filtered waveform windows** from the original recordings. It verifies source checksums, window alignment, and agreement with the feature table's RMS values. Feature models and the CNN therefore use the same labelled windows.

### Validation and fixed settings

Outer evaluation uses leave-one-subject-out cross-validation. Both legs and all recordings from a participant remain in the same partition. Feature selection, imputation, scaling, and hyperparameter searches are fitted within grouped inner validation on training participants. The majority baseline has no tuning.

The CNN uses a fixed architecture, training-only amplitude scaling, and no inner search or early stopping. Its settings are **20 epochs, batch size 128, learning rate 0.001, weight decay 0.0001, and dropout 0.2**, defined in `CNN_CONFIG`. The base random seed is **20261018**; fold-specific seeds and final refit settings are recorded by the runners. No class weighting or resampling is applied.

Generate the descriptive class-imbalance tables separately with:

```sh
python -m modelling.class_balance
```

The notebooks display these class counts automatically. Command-line runs generate evaluation outputs without filling notebook cells. After held-out evaluation, each model also saves a final model fitted on all participants; that refit has no additional independent test score.

## Results and figures

Each experiment writes a timestamped run directory under `modelling/outputs/<model>/`. The corresponding `modelling/outputs/latest_<model>.json` identifies its latest completed run.

After all six experiments finish using the same inputs and source version, combine their results:

```sh
python -m modelling.export_results
```

This writes `results.csv` at the repository root, with one row per model and held-out fold and all ten evaluation metrics. It also writes `modelling/outputs/report_metrics_mean_sd.csv`, containing the six-model comparison. The exporter checks completion, dataset compatibility, held-out participants, and shared evaluation code. The separate automatically generated `modelling/outputs/results.csv` covers only models 01–04.

Primary summaries give each held-out participant equal weight and report the mean and sample standard deviation across folds. The metrics are accuracy, macro precision, macro recall, macro F1, F1 for each class, Cohen's kappa, ROC-AUC, trapezoidal PR-AUC, and average precision.

| Output | Location within a model's run directory |
| --- | --- |
| Fold metrics | `results.csv` |
| Mean and sample SD across folds | `metrics_mean_sd.csv` |
| Per-class metrics | `per_class_metrics.csv`, `per_class_mean_sd.csv` |
| Confusion counts and row-normalized proportions | `confusion_counts.csv`, `confusion_row_normalized.csv`, `figures/confusion_matrices.png` |
| Per-subject performance | `per_subject_metrics.csv`, `figures/per_subject_f1.png` |
| Validation diagram | `figures/validation_diagram.png` |
| Feature selection stability, where applicable | `selection_frequency.csv` and individual fold artifacts |
| Bilateral performance | `per_subject_leg_metrics.csv`, `paired_leg_f1.csv` |
| Versions, device, timings, settings, and input hashes | `run_manifest.json` |
| Final model | `final_refit/` |

Class-imbalance outputs are stored separately under `modelling/outputs/class_balance/<data-hash>/`. Feature trajectories and Figure 2 are generated by the preprocessing command under the run identified in `processing/outputs/latest_run.json`. Trajectories describe elapsed-time progression with equal-set and equal-subject aggregation.

### Interpretation

Feature-selection frequencies describe selection stability rather than statistical significance or a controlled ablation. Bilateral performance tables compare scores by leg; they do not establish dominance effects or simultaneous inter-leg signal relationships. Interpretation must account for the elapsed-time labels, manual boundary and QC decisions, unavailable MVC and resting-reference measurements, and any differences between the planned acquisition protocol and the available recordings.
